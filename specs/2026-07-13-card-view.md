# Spec: Contact card view toggle (issue #10)

**Problem.** `_contacts.html` renders only a flat list. Users want a card/grid view,
switchable with the list, persisted per user.

**Intended behavior.**

1. **Persistence & plumbing.** The active view lives in a cookie (`peopledb_view`,
   values `list`/`card`, default `list` when absent/invalid). Server-side rendering
   reads it in both `index` and `search` routes and passes `view` into the template
   context, so the HTMX search fragment automatically renders in the active layout —
   no client-side re-layout. A tiny route `POST /view` (form value `view=list|card`)
   sets the cookie (1-year max-age, samesite=lax, NOT httponly-sensitive — it's a UI
   pref) and redirects back to `/` (303).
2. **Toggle UI.** In the index page's toolbar (near the group controls), a small
   two-state control (e.g. buttons "List ⁄ Cards", active one highlighted) posting to
   `/view`. Only on the index page — detail/group pages are unaffected.
3. **Card layout.** In `_contacts.html`, when `view == "card"`: a responsive CSS grid
   (`repeat(auto-fill, minmax(~180px, 1fr))`) of cards, each showing the avatar (reuse
   the existing `_avatar.html` macro, large size), name (link to detail), org when
   present, and primary (first) phone and email when present. List view stays exactly
   as-is and remains the default. Empty state ("No contacts found.") works in both.
4. **Search.** `/search` results render in whichever view is active — the fragment
   template already receives `view` per (1). The `group` filter view (index with
   `?group=`) uses the same layout rules.

**Out of scope.** Per-device vs per-user distinction (cookie is per-browser — fine);
sorting changes; pagination; touching detail/group/birthdays pages.

**Test approach.** TDD route/template tests (non-live where the store can be seeded
directly): default is list; `POST /view` sets cookie + redirects; index with
`peopledb_view=card` renders the grid markup incl. avatar/org/phone; search fragment
respects the cookie; invalid cookie value falls back to list. Visual check in browser
(both themes) after.
